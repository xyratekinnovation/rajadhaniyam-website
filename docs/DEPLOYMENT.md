# Deployment (Render + Supabase)

## Why these choices

- **Render** hosts all three apps. Bun has no native Render runtime, so
  `apps/api` and `apps/storefront` deploy as `docker` services (see their
  `Dockerfile`s) built from the repo root — Docker context must be the root,
  not the app subdirectory, because `bun install` needs every workspace
  member's `package.json` present to resolve `workspace:*` dependencies.
  `apps/admin` is a static build (no server needed for a CSR SPA), so its
  Render service installs Bun via the official install script during the
  build step instead of using Docker.
- **Supabase** provides the Postgres database for `packages/database`'s
  Prisma schema (Phase 2). Free tier is enough until real traffic arrives.
- Both docker web services (`rajadhaniyam-api`, `rajadhaniyam-storefront`)
  use Render's **free** plan, which doesn't require a card on file — the
  tradeoff is the service spins down after ~15 min of no traffic and takes
  30-60s to cold-start on the next request. Switch `render.yaml`'s
  `plan: free` to `plan: starter` (paid, ~$7/mo/service, genuinely
  always-on) once this needs to stay warm for real customers — the only
  actual fix, since it removes the idle spin-down entirely.
- `.github/workflows/keep-warm.yml` pings both services every 10 minutes
  (under the 15-min idle threshold) as a free stopgap so they rarely go
  fully idle during normal operation. It's a workaround, not a real fix:
  it can't prevent a cold start right after a fresh deploy or a Render-side
  restart, and GitHub can skip/delay scheduled runs under load. Scheduled
  workflows are also auto-disabled after 60 days with no commits to the
  repo — if pings stop, check the Actions tab and re-enable it, or push
  anything to reset the clock.

## One-time setup

1. **Supabase**: create a project at supabase.com → Project Settings →
   Database → copy the **connection string** (URI, "Transaction" pooler
   mode for serverless-friendly connections). This becomes `DATABASE_URL` —
   append `?pgbouncer=true` to it, or every Prisma query fails with
   `prepared statement "s0" already exists`. `apps/api` only needs this
   pooled URL; `DIRECT_URL` (the non-pooled, port 5432 connection) is only
   needed locally, for running `prisma migrate`.
2. **Render**: sign up at render.com with GitHub → New → **Blueprint** →
   select `xyratekinnovation/rajadhaniyam-website` → Render reads
   [`render.yaml`](../render.yaml) at the repo root and proposes all three
   services at once.
3. After the first deploy, open each service's **Environment** tab and fill
   in the variables marked `sync: false` in `render.yaml`:
   - `rajadhaniyam-api`: `DATABASE_URL` (from Supabase), `SUPABASE_URL` and
     `SUPABASE_SERVICE_ROLE_KEY` (Project Settings → API — needed for
     product/category image uploads, Phase 4),
     `PAYMENT_PROVIDER_KEY` / `PAYMENT_PROVIDER_SECRET` (Razorpay Key ID /
     Key Secret), and `PAYMENT_WEBHOOK_SECRET` (from Razorpay Dashboard →
     Webhooks after you create the webhook). Webhook URL:
     `https://rajadhaniyam-api.onrender.com/payments/webhook`
     (events: `payment.captured`, `payment.failed`).
     `JWT_SECRET`/`SESSION_SECRET` are auto-generated by Render
     (`generateValue: true`) — no action needed.
4. Redeploy `rajadhaniyam-api` after adding those so it picks up the new
   env vars.
5. Run `bun run --cwd=apps/api setup-storage` once (locally, with
   production `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` in the shell env)
   to create the `product-images` bucket — it's idempotent, safe to re-run,
   and only needs to happen once per Supabase project (already done for
   the current one).
6. Admin login already works against a Render deploy without further
   setup — `bun run --cwd=apps/api create-admin` was already run once
   against the shared Supabase database (Phase 5), and every environment
   pointed at that same `DATABASE_URL` (local dev, Render) shares the same
   `AdminUser` rows. Only run `create-admin` again to provision an
   *additional* admin account or reset a password, not "to make prod work"
   the current one).

## Known URLs (predicted, verify after first deploy)

Render assigns `<service-name>.onrender.com` by default. `render.yaml`
wires the three services together using the *predicted* names below — if
Render assigns different ones (name collision), update the corresponding
`STOREFRONT_URL`/`ADMIN_URL`/`VITE_API_BASE_URL`/`VITE_ADMIN_URL` env vars
on each service to match reality:

- API: `https://rajadhaniyam-api.onrender.com`
- Storefront: `https://rajadhaniyam-storefront.onrender.com`
- Admin: `https://rajadhaniyam-admin.onrender.com`

## Custom domain

Once `rajadhaniyam.in` (the project's production domain) is ready to point at
Render: Render dashboard → service → Settings → Custom Domains → follow the
DNS instructions (usually a CNAME to the `.onrender.com` host). Do this for
the storefront service; the admin can stay on a subdomain
(`admin.rajadhaniyam.in`) or the default `.onrender.com` URL since it's
internal-only.

## Platform-specific gotchas fixed for this deploy

- `apps/storefront/vite.config.ts` pins Nitro's `preset: "node-server"`.
  Without this, the build defaults to Cloudflare Workers output
  (`cloudflare-module`), which Render's Docker service cannot run — Render
  runs a persistent container, not a Workers isolate.
- `apps/api/src/config/env.ts` reads Render's `PORT` env var (falling back
  to `API_PORT`/`4000` locally), since Render assigns the port a web service
  must bind to — it isn't fixed and isn't controlled by us.
- `apps/api/Dockerfile` runs `prisma generate` at build time even before a
  real `DATABASE_URL` exists, because `@rajadhaniyam/database` imports
  `PrismaClient` eagerly at module load — without a generated client, the
  API container fails to boot at all, not just on first query.
- `apps/storefront/Dockerfile` declares `ARG VITE_API_BASE_URL`/
  `ARG VITE_ADMIN_URL` before its build step. Docker builds don't see a
  service's env vars by default, but Render re-injects them as build args
  with matching names — without the `ARG` line, Vite bakes in nothing for
  those vars and the deployed SSR pages fail every API call at runtime
  with "Unable to connect. Is the computer able to access the url?" (found
  on the first real Phase 15 deploy). `apps/admin` doesn't need this: its
  build runs as a plain Render static-site build command, not inside
  Docker, so it already sees env vars normally.
