# Architecture

## Why this layout

Rajadhaniyam started as a single Lovable-generated **TanStack Start** app
(SSR + file-based routing + server functions in one Vite build). This phase
restructures it into a Bun workspace monorepo without touching its working
frontend, in preparation for a real backend, admin panel, and database.

```
/
├── apps/
│   ├── storefront/   # customer-facing site — TanStack Start (SSR), unchanged behavior
│   ├── admin/         # admin dashboard — Vite + React + TanStack Router (CSR, no SSR)
│   └── api/           # backend API — Hono on Bun, modular routes
├── packages/
│   ├── shared/         # cross-app types, Zod schemas, constants, utils
│   ├── database/       # Prisma schema + client (not connected yet)
│   ├── ui/              # seed for a future shared component library
│   └── config/          # shared tsconfig base
└── docs/
```

## Key decisions (and why they deviate from a generic template)

**`apps/storefront` stays a single TanStack Start app, not split into a
"pure frontend".** TanStack Start couples routing, SSR and server functions
into one Vite build (`src/router.tsx`, `src/start.ts`, `src/server.ts`,
generated `src/routeTree.gen.ts`). Splitting the SSR shell out from its
routes would fight the framework for no benefit — instead, backend business
logic (orders, payments, inventory, DB access) lives in `apps/api`, and the
storefront only talks to it through `apps/storefront/src/services`.

**`apps/admin` is a plain CSR SPA, not a second TanStack Start app.** An
authenticated back-office dashboard doesn't need SSR. Using
`@tanstack/react-router` directly (code-based route tree, no
`routeTree.gen.ts`) keeps the admin app simple and avoids a second Nitro/SSR
server to operate. It shares `@rajadhaniyam/shared` types with the
storefront and API.

**`apps/api` is a separate Hono service on Bun**, not routes bolted onto
TanStack Start. This keeps business logic (auth, orders, payments, DB
queries) decoupled from the SSR framework, so it can be called by both the
storefront and the admin app, and evolved independently.

**`packages/ui` is intentionally a seed, not a full component migration.**
The storefront's ~40 shadcn/Radix components are wired tightly to its
`components.json` and Tailwind theme; moving them now would be a large,
risky change for no immediate consumer (the admin app has its own minimal
placeholder UI). Extracting real shared primitives is a good later-phase
task once the admin's design requirements stabilize.

**The mock catalog (`src/lib/shop-data.ts`) was not deleted.** A
repository/service abstraction (`src/services/products`,
`src/services/categories`) now sits in front of it. Swapping
`MockProductRepository` for an `ApiProductRepository` later is a one-line
change — no UI component needs to be rewritten.

## Data flow (current state)

```
storefront route loader ──▶ productService / categoryService ──▶ MockProductRepository ──▶ shop-data.ts (hardcoded)
```

## Data flow (after Phase 3 of the roadmap)

```
storefront route loader ──▶ productService ──▶ ApiProductRepository ──▶ apps/api /products ──▶ packages/database (Prisma) ──▶ PostgreSQL
```

## Generated files — do not hand-edit

- `apps/storefront/src/routeTree.gen.ts` — regenerated by
  `@tanstack/router-plugin` on every `dev`/`build`. Edit route files under
  `apps/storefront/src/routes/` instead.
- `apps/admin` has **no** generated route tree — its routes are defined in
  code in `apps/admin/src/router.tsx`, so there is nothing to regenerate.

## Lovable-specific pieces (kept)

- `@lovable.dev/vite-tanstack-config` (in `apps/storefront/vite.config.ts`)
  bundles TanStack Start + React + Tailwind + nitro + sandbox
  detection. Removing it would require hand-rebuilding all of that — kept
  as-is.
- `apps/storefront/src/lib/error-capture.ts`, `error-page.ts`,
  `lovable-error-reporting.ts` — wired into SSR error handling
  (`start.ts`, `server.ts`, `routes/__root.tsx`). Kept as-is; they're what
  render the friendly 500 page.
- `.lovable/project.json`, `bunfig.toml`'s `minimumReleaseAgeExcludes`,
  `AGENTS.md`'s Lovable notice — kept, harmless project metadata.
